# Подробное руководство

[← На главную](../README.md)

Установка, настройка и обслуживание бота. Все команды выполняются
из корня проекта, если не указано иное.

## Настройки

Настройки и секреты задаются в **config.py**. Скопируй шаблон
[config.example.py](../config.example.py), укажи токен бота и список `users`.
Username можно писать с `@` или без него;
регистр не учитывается. Пользователь без username также не получает доступ.
Любому пользователю вне списка бот отвечает ровно `🔐 У вас нет доступа.`.
Разрешённые пользователи используют бота в личных сообщениях.

Для добавления пользователей:

```python
users = ["username1", "username2"]
```

После изменения настроек перезапусти бота. `config.py`, cookies, скачанные файлы
и журналы исключены из Git. `config.example.py` — шаблон без токена для переноса
проекта; если личного конфига нет, скопируй его в `config.py` и заполни.

## Установка и запуск

Нужны Python 3.10+, **FFmpeg вместе с ffprobe** и **Node.js 22+** либо Deno 2.3+.
Современный yt-dlp использует JavaScript runtime и EJS для обработки YouTube:
[официальная инструкция](https://github.com/yt-dlp/yt-dlp/wiki/EJS).
EJS устанавливается вместе с `yt-dlp[default]` из requirements.txt.

Минимальная версия yt-dlp — `2026.10.10.233141.dev0`: она содержит исправление
YouTube-клиента для ошибки `The page needs to be reloaded`, встречавшейся
при использовании cookies. Эта нижняя граница допускает исправленную nightly
при обычной установке requirements; будущие стабильные версии также подходят.
[Исправление upstream](https://github.com/yt-dlp/yt-dlp/pull/17805).

macOS с Homebrew:

```bash
brew install python@3.12 ffmpeg node
```

Ubuntu/Debian: установи `python3`, `python3-venv`, `ffmpeg` и Node.js 22+.
На Windows установи те же инструменты и добавь их в PATH.
Если FFmpeg находится отдельно, укажи каталог в `FFMPEG_DIR`;
для нестандартного пути Node.js используй `JS_RUNTIME_PATH`.
При запуске бот проверяет не только наличие Node.js/Deno, но и минимальную
версию: Node.js 22.0.0 или Deno 2.3.0. Node.js 18 из стандартного репозитория
Ubuntu 24.04 для текущего yt-dlp не подходит: JS challenge может завершаться
ошибкой, после чего yt-dlp видит только изображения и сообщает
`Requested format is not available` ещё до появления меню качества.

Если другие приложения используют системный Node.js, установи официальный
Linux-архив Node.js 22 отдельно, например в `/opt/youtube-downloader/runtime/node22`,
и задай в конфиге бота:

```python
JS_RUNTIME = "node"
JS_RUNTIME_PATH = "/opt/youtube-downloader/runtime/node22/bin/node"
```

Бинарник можно проверить командой с полным путём и параметром `--version`.
Путь передаётся yt-dlp явно; менять глобальный PATH или системный Node.js для
этого не требуется. [Официальные требования EJS](https://github.com/yt-dlp/yt-dlp/wiki/EJS).

По умолчанию шаблон подключается к [локальному Bot API](bot-api.md). Настрой
его перед запуском для отправки файлов до 2000 МБ. Для облачного API с лимитом
50 МБ укажи `BOT_API_URL = None`. Боту нужен прямой доступ к YouTube, включая
`googlevideo.com`.

Из каталога проекта:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -c "import sys; assert sys.version_info >= (3, 10), 'Нужен Python 3.10 или новее'"
python -m pip install -r requirements.txt
python bot.py
```

В Windows активация: `.venv\Scripts\activate`.
В Linux укажи установленный Python 3.10+ вместо `python3.12`, в Windows — `py -3.12`.
Остановка: **Ctrl+C**. Одновременно запускай только один экземпляр бота с этим токеном.

Можно использовать уже установленный `uv`:

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python bot.py
```

Если при установке появляется `Requires-Python >=3.10`, проверь `python3 --version`
и `pip3 --version`: на macOS они могут указывать на системный Python 3.9,
даже когда новый Python уже установлен. Используй интерпретатор окружения явно:

```bash
.venv/bin/python --version
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python bot.py
```

Если окружение создано через `uv` и внутри нет pip, устанавливай через
`uv pip install --python .venv/bin/python -r requirements.txt` либо добавь pip
командой `.venv/bin/python -m ensurepip --upgrade`.
Если сама `.venv` использует Python ниже 3.10, создай новое окружение
`python3.12 -m venv .venv312` и используй `.venv312/bin/python`.

## Использование

Для постоянной работы Python-бота на Linux используй
[службу systemd](python-service.md) с автозапуском и перезапуском после сбоя.

1. Открой бота в Telegram под аккаунтом из списка `users`, отправь `/start`.
2. Пришли ссылку на видео, Shorts или плейлист. Если ссылка содержит и видео,
   и `list=…`, бот предложит скачать только видео либо весь плейлист.
3. Выбери **MP3**, **MP4 · лучшее** или разрешение: **144p**, **240p**, **360p**,
   **480p**, **720p**, **1080p**, **2K · 1440p**.
   Для отдельного видео показываются только реально найденные разрешения.
   Перед меню плейлиста проверяются все ролики: показываются только разрешения,
   общие для каждого из них. Ход проверки виден в том же сообщении и через `/status`;
   её можно прервать командой `/cancel`. Проверка длинного плейлиста занимает время.
   Если какой-либо ролик проверить не удалось, непроверенные кнопки не показываются:
   бот указывает номер проблемного видео. Для MP3 требуется доступный аудиопоток;
   MP4 и разрешения предлагаются только при наличии доступного видеопотока.
   MP4 означает контейнер и лучшее доступное качество, поэтому может быть и 4K.
   Качество учитывает ориентацию: 1080p — это 1920×1080 для обычного кадра 16:9
   и 1080×1920 для вертикального 9:16. Ограничивается короткая сторона кадра;
   число 1080 в высоте вертикального файла само по себе не означает качество 1080p.
   Это применяется к кнопкам меню, обычному скачиванию и HLS.
   Выбранное разрешение соблюдается точно, в том числе в плейлистах и при выборе HLS-потока.
   Если доступный поток такого качества получить нельзя, бот сообщает об ошибке
   для этого ролика. Подмена меньшим разрешением и искусственное увеличение запрещены.
   Если нужного разрешения нет в ответе YouTube, бот сразу показывает доступные
   разрешения и максимум. Для плейлиста с разным исходным качеством выбирай
   **MP4 · лучшее**, чтобы каждый ролик скачался в своём максимальном разрешении.
4. Получай файлы в чат. `/status` показывает состояние задачи, `/cancel` отменяет её,
   `/help` показывает справку.

### Рассылка администратора

Сразу под `users` в `config.py` указывается администратор:

```python
users = ["username1", "username2"]
ADMIN_BOT = "admin_username_tg"
```

Администратор тоже должен находиться в `users`. Команда `/all Текст сообщения`
отправляет обычный текст всем пользователям из текущего `users`, включая
администратора, если его чат известен. Переносы строк сохраняются.
Посторонние пользователи и удалённые из `users` не получают рассылку, даже если
раньше писали боту. Перед отправкой username чата дополнительно сверяется с Telegram.
Остальным пользователям команда отвечает `🔐 У вас нет доступа.`

После установки обновления каждому участнику нужно один раз отправить `/start`
или другое сообщение боту. Так бот узнаёт chat_id; одних личных username для
рассылки недостаточно. Соответствия сохраняются в `USERS_DB_PATH`
(по умолчанию `data/users.sqlite3`), поэтому после перезапуска повторять `/start`
не требуется. База не заменяет список доступа и исключена из Git.

В конце администратор получает итог: количество отправленных сообщений, ошибок,
неизвестных чатов и пропущенных получателей со сменившимся username. Ошибка одного
получателя не останавливает остальных. Неоднозначные сетевые ошибки отправки
не повторяются, чтобы избежать дубликатов; ограничения Telegram `RetryAfter`
учитываются. Начало, результаты и получатели рассылки журналируются в
`logs/downloads.log`; содержимое сообщения не записывается.

### Прогресс скачивания

Сообщение с выбором формата становится **одним обновляемым сообщением прогресса**
на всю задачу, включая весь плейлист. Оно показывает текущий ролик и его название,
пакет, этап обработки, количество отправленных роликов и ошибок. При скачивании
отображаются процент, скорость в МБ/с и полученный объём; при отправке — процент,
объём, средняя скорость и прошедшее время. В конце в этом же сообщении появляется итог.
После успешной отправки всех роликов плейлиста дополнительно приходит отдельное
уведомление: «✅ Готово. Все видео (N) из плейлиста отправлены». При ошибках или
отмене такое подтверждение полной отправки не посылается.

YouTube может отдавать видео и аудио отдельными потоками: процент относится
к текущему потоку и может начаться заново при переходе к аудио. Если размер
потока неизвестен, показывается полученный объём без выдуманного процента.
При подготовке MP4 для галереи FFmpeg сообщает фактически обработанную длительность:
бот показывает полосу прогресса, процент, прошедшее время и примерное оставшееся
время по текущей скорости. До проверки готового файла процент ограничен 99%.
Для этапов yt-dlp без измеримого прогресса показывается прошедшее время.
Рядом с выбранным качеством отображается фактическое разрешение MP4,
например `1920×1080`. Подготовка H.264/AAC сохраняет разрешение; это выбор кодеков
для совместимости с медиатекой телефона.

Получение метаданных YouTube ограничено общим сроком `METADATA_TIMEOUT = 120`
секунд. При тайм-ауте или `/cancel` завершается отдельный процесс yt-dlp вместе
с его Node.js/Deno, а сообщение обновляется с причиной остановки. Предупреждения
yt-dlp и время получения информации записываются в `logs/bot.log`. Если заняты
все рабочие места, сообщение явно показывает ожидание очереди.
При сетевой ошибке обычного видеопотока бот может запросить HLS-поток,
если он доступен у YouTube. Для HLS бот получает свежие метаданные и сохраняет
выбранное разрешение. При наличии HLS сетевой тайм-аут попытки задаёт
`YOUTUBE_FALLBACK_TIMEOUT` (10 секунд по умолчанию). MP3 в этом случае
извлекается локально из потока с видео, что увеличивает объём скачивания.
Ошибка фрагмента прерывает загрузку. Части разных потоков хранятся раздельно.
Прогресс отправки считается по чтению файла потоковым HTTP-клиентом; это ещё
не подтверждение получения файла Telegram. До успешного ответа процент ограничен
99%, а после чтения файла отображается ожидание подтверждения доставки.
Если новых данных нет 15 секунд, статус показывает длительность паузы;
счётчик времени продолжает обновляться. Каждые 30 секунд ход отправки пишется в журнал.
Обновление — раз в `PROGRESS_UPDATE_INTERVAL` секунд (по умолчанию 3);
одинаковые состояния повторно не отправляются. Ограничение частоты Telegram
(`RetryAfter`) учитывается. Сетевой сбой обновления не прерывает скачивание.
По явной команде `/status` бот отвечает отдельной текущей сводкой пользователя.

Плейлисты любой длины, включая 20+ видео, обрабатываются **пакетами по 5**.
Список роликов фиксируется при показе меню форматов и повторно не запрашивается
при нажатии кнопки. Чтобы обновить список, отправь ссылку ещё раз.
Внутри пакета файлы скачиваются и отправляются по одному. После отправки
пакета бот автоматически переходит к следующему. Ошибка отдельного ролика
не прерывает остальные; недоступные/удалённые записи могут завершиться ошибкой
либо быть пропущены самим YouTube. Прямые эфиры и ожидающие премьеры не скачиваются.
Динамические YouTube Mix могут содержать только ту часть списка, которую выдаёт YouTube.

У пользователя может быть одна активная задача. Разные разрешённые пользователи
обслуживаются параллельно до `MAX_CONCURRENT_JOBS`; остальные ждут в очереди.
Отменённая задача выходит из очереди, не дожидаясь завершения чужих скачиваний.
Меню выбора хранятся в памяти один час. После перезапуска отправь ссылку заново;
очередь не восстанавливается. При запуске бот сбрасывает накопленные обновления Telegram:
команды, ссылки и нажатия кнопок, отправленные во время отключения, не обрабатываются.
Отмена во время запроса к YouTube или конвертации
yt-dlp сработает после завершения текущего запроса/этапа.

## Размер файлов

Облачный Telegram Bot API позволяет ботам загружать файлы до 50 MB:
[Telegram FAQ](https://core.telegram.org/bots/faq#how-do-i-upload-a-large-file).
Установлен запас: `TELEGRAM_FILE_LIMIT = 49_000_000` байт.
Бот отправляет один цельный файл на ролик и не разрезает запись.
MP3 по умолчанию кодируется в 128 кбит/с (`MP3_BITRATE`): запись длительностью
23:25 занимает примерно 22,5 МБ. При 320 кбит/с она занимала бы около 56,2 МБ.
После скачивания длительность MP3 проверяется через ffprobe и сравнивается
с длительностью из метаданных YouTube; после уменьшения размера проверка повторяется.
При несовпадении более чем на 2 секунды (или 0,1% для длинных записей)
бот сообщает об ошибке и не отправляет неполный файл.
Если MP3 превышает лимит, FFmpeg уменьшает битрейт, сохраняя полную длительность.
Битрейт выбирается по длительности и доступному размеру, не ниже
`MP3_MIN_BITRATE = 64` кбит/с; итоговый размер проверяется перед отправкой.
Это снижает качество звука. Выбранный битрейт отображается в статусе.
Если MP4 слишком большой или MP3 не помещается даже при минимальном битрейте,
бот сообщает причину без отправки фрагментов. Для MP4 можно выбрать качество ниже.
Для больших файлов без уменьшения качества нужен
[локальный сервер Bot API](https://core.telegram.org/bots/api#using-a-local-bot-api-server)
с лимитом загрузки 2000 MB. Подключение поддерживается через `BOT_API_URL`;
установка и запуск описаны в [инструкции по локальному Bot API](bot-api.md).
Для собственного API используется `BOT_API_FILE_LIMIT = 1_950_000_000`, а облачный
`TELEGRAM_FILE_LIMIT` остаётся прежним. API должен быть запущен с `--local`.
Для видео бот предпочитает H.264 и AAC при одинаковом разрешении. Перед отправкой
ffprobe проверяет фактические кодеки и длительность: расширение `.mp4` само по себе
не гарантирует совместимость с галереей iPhone. AV1, VP9, 10-битное видео и другие
несовместимые потоки преобразуются в MP4 с H.264 (8 бит, yuv420p) и AAC-LC;
HDR при преобразовании переводится в SDR. Разрешение и полная длительность сохраняются
(нечётные размеры дополняются до ближайших чётных). Индекс MP4 помещается в начало
файла для потокового воспроизведения. Telegram получает фактические размеры и длительность.
Совместимые потоки копируются без повторного кодирования; готовый совместимый MP4
с индексом в начале отправляется без дополнительной обработки. Преобразование в H.264
может увеличить размер и время обработки, особенно для 2K/4K. По умолчанию используется
один поток FFmpeg (`VIDEO_THREADS = 1`) и `VIDEO_CRF = 20`. Эти параметры необязательны
в существующем `config.py`. Если Telegram отклоняет видео/аудио, файл отправляется документом.
MP3 на iPhone сохраняют в приложение «Файлы», а не в «Фото».

Видео, аудио и временные каталоги удаляются после каждого ролика:
после успешной отправки, ошибки скачивания или отправки и отмены.
Оригинал удаляется после подготовки уменьшенного MP3, а итоговый файл —
сразу после его успешной отправки. Передача в Telegram идёт потоком с диска,
без чтения всего файла в оперативную память.
При перекодировании на диске находятся оригинал и подготовленный MP3/MP4: нужно место для обоих.
После аварийного завершения процесса остатки можно удалить из `downloads/`
при остановленном боте.

## Журнал действий

`logs/downloads.log` — отдельный журнал JSON Lines, по JSON-объекту на строку:

```json
{"time":"2026-10-18T12:00:00+00:00","event":"delivered","user_id":123456789,"username":"SomeUsernameInTg","url":"https://www.youtube.com/watch?v=Z_y-8-u8H5s","title":"Пример видео","quality":"1080","parts":1}
```

Фиксируются запрос, начало скачивания, скачанный файл, начало отправки,
успешная доставка, ошибки, отмена и отказ в доступе. Есть username и Telegram ID,
URL, название и качество; успешная доставка отмечается только после подтверждения Telegram.
Время — UTC. `logs/bot.log` — технический журнал. Для обоих журналов настроена
ротация: 10 MB на файл и 5 архивов; токен маскируется.

## Если YouTube требует вход

При ошибке `The page needs to be reloaded` останови Python-бота, обнови зависимости
в его виртуальном окружении и снова запусти его:

```bash
.venv/bin/python -m pip install --upgrade -r requirements.txt
.venv/bin/python -m yt_dlp --version
```

Для уже перенесённого проекта со старым requirements.txt официальный способ
обновить только загрузчик до nightly вместе с подходящим EJS:

```bash
.venv/bin/python -m pip install --upgrade --pre "yt-dlp[default]"
```

[Рекомендация разработчиков по этой ошибке](https://github.com/yt-dlp/yt-dlp/issues/17389).
Перезапуск нужен, потому что работающий процесс уже импортировал прежнюю версию.
Если обновление не помогло, проверь на сервере версию выбранного JS runtime
(`node --version` или `deno --version`) и журнал `logs/bot.log`.

При необходимости укажи `COOKIE_FILE = "cookies.txt"` с экспортом cookies
в формате Netscape. Экспортировать cookies можно по
[официальной инструкции yt-dlp](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#exporting-youtube-cookies).
Положи `cookies.txt` рядом с `bot.py` и перезапусти приложение.

Перед отправкой бот показывает размер цельного файла. Базовый бюджет отправки
и таймаут отдельной сетевой операции — `UPLOAD_TIMEOUT` (180 секунд по умолчанию).
Общий бюджет для больших файлов рассчитывается по размеру и
`UPLOAD_MIN_BYTES_PER_SECOND` (64 000 байт/с), но не превышает
`UPLOAD_MAX_TIMEOUT` (900 секунд). Например, файл 32 МБ получает около 530 секунд,
а не прерывается через 180 секунд на медленном, но работающем соединении.
При заданном `BOT_API_URL` максимальный общий бюджет и ожидание ответа после
передачи файла задаются `BOT_API_UPLOAD_TIMEOUT` (по умолчанию 7200 секунд).
Прогресс чтения файла отражает передачу Python → API; после этого ожидается
подтверждение отправки от самого API. Это не процент его загрузки в Telegram.
Это предотвращает лишние повторные скачивания, а не повышает пропускную способность.
Ошибки установления
соединения повторяются до `TELEGRAM_UPLOAD_ATTEMPTS` раз; ошибки после начала
передачи автоматически не повторяются, поскольку Telegram мог уже принять файл.
`/cancel` прерывает ожидание отправки. Журнал содержит начало/окончание отправки
и цепочку причин сетевой ошибки.
Ошибка обновления сообщения прогресса записывается в журнал и не прерывает
скачивание и отправку файлов. Токен и учётные данные в URL маскируются в ошибках.
После изменений на стороне YouTube обновляй библиотеку:

```bash
python -m pip install --upgrade -r requirements.txt
```

## Производительность

После выбора формата бот использует уже полученные метаданные одиночного видео,
если им не больше `METADATA_CACHE_TTL` секунд (по умолчанию 120). Если URL медиапотока
устарел и вернул HTTP 403/410, информация запрашивается заново один раз.
Выбор MP3/MP4 и разрешения применяется повторно к исходному списку форматов.

Для DASH/HLS включено `DOWNLOAD_CONCURRENT_FRAGMENTS = 4`: фрагменты одного
ролика скачиваются параллельно. На обычные цельные HTTP-файлы этот параметр
не влияет. Кэш служебных данных yt-dlp хранится в `YTDLP_CACHE_DIR`
(`.cache/yt-dlp`), отдельно от временных видео.

В `logs/downloads.log` событие `performance` содержит время в секундах:
`download_prepare_seconds` — получение/скачивание и обработка,
`postprocess_seconds` — часть этого времени, затраченная на постобработку,
`prepare_upload_seconds` — подготовка цельного файла, `upload_seconds` — отправка в Telegram,
`total_seconds` — общее время ролика. При ошибке также сохраняются доступные замеры.
Технический журнал дополнительно показывает фактическую скорость отправки в МБ/с.

Если основное время занимает отправка, проверь пропускную способность
исходящего соединения сервера с Telegram.

## Проверка

```bash
python -m unittest discover -s tests -v
```

Проверяются доступ, URL, качество, привязка кнопок к пользователю, журнал,
обработка 21 видео пакетами, продолжение после ошибки, отмена и очистка.
Также проверяются выбор разрешения реальным селектором yt-dlp, отмена в очереди,
передача файла через HTTP-клиент Telegram с локальным подменным транспортом
и завершение фоновой записи до удаления временного каталога при отмене.
Проверяются также состояние `/status`, редактирование одного сообщения на весь
плейлист, hooks прогресса, скорость/процент, обработка `RetryAfter` и остановка
фонового обновления после завершения или отмены.
Проверяются также повторное использование метаданных при настоящей конвертации
локального тестового файла, обновление устаревшего URL и расчёт бюджета отправки.
С FFmpeg/ffprobe дополнительно проверяются преобразование VP9/Opus в H.264/AAC,
перевод 10-битного HDR в SDR, сохранение длительности, пропуск повторного кодирования
совместимых файлов, очистка при ошибке/отмене и уменьшение цельного MP3
с контролем размера и сохранения длительности, отказ от нарезки большого MP4, а также скачивание локального
тестового файла через yt-dlp и конвертация в MP3. Тесты не обращаются к Telegram/YouTube.
